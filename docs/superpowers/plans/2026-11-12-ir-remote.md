# IR remote for the yellow deck

Status on 2026-11-12: hardware wired on the bench, test sketch written and building, **nothing flashed
yet**, no button codes captured. This plan is the handoff for the session that adds the feature.

## Goal

The car's outside LED kit came with a 24-button IR remote, but its own IR receiver sits outside the
car, so the remote was useless from the seats. A KY-022 IR receiver on the yellow deck (CYD) lets the
Owner aim that remote at the deck inside the car; the deck then drives both lights over BLE exactly as
a tap, a voice command or the PS3 controller does. The remote becomes a fourth input next to touch,
voice (`/say`) and the pad.

There is no double-trigger risk: the LED kit's receiver is outside and only reacts when aimed at
directly from outside, so presses aimed at the deck reach the deck only.

## Hardware (done, not yet powered with the module on)

- **Module:** KY-022, a VS1838B-style 38 kHz demodulating receiver. Output idles HIGH, pulses LOW. Its
  board has a pull-up to its VCC, so it **must be powered from 3.3 V** (5 V would put 5 V on an ESP32
  pin). Pins on the module: `S` (signal), middle (VCC), `-` (GND). On the Owner's module, `S` is the
  end pin marked "S" and `-` is the opposite end.
- **Board:** ESP32-2432S028 "Cheap Yellow Display", the **two-USB revision** (micro-USB + USB-C side
  by side). Backlight on GPIO 21, touch on 25/32/33/36/39, TFT on 2/12/13/14/15 (`include/pins.h`,
  `platformio.ini` `[cyd]`).
- **Connector:** CN1, the 4-pin JST 1.25 mm socket next to the RGB LED (the other 4-pin socket, P3,
  is unused). CN1 carries 3.3V, IO27, IO22 and GND. **Free in every yellow build:** neither the
  firmware nor `pins.h` touches GPIO 22, 27 or 35.
- **Cable:** the JST 1.25 to 4 × Dupont cable that came with the board. Wires down the plug as
  photographed (USB at the top): red, yellow, blue, black.

| CN1 pin | Wire | KY-022 pin |
|---|---|---|
| 3.3V | red | middle (VCC) |
| IO27 | yellow | `S` |
| IO22 | blue | unused, tip taped |
| GND | black | `-` |

**Unverified:** the CN1 pin order comes from Random Nerd Tutorials' photos of the single-USB board
(CN1 silkscreen, left to right with the SD slot left: 3.3V, IO27, IO22, GND) plus the cable colours
agreeing with it. The silkscreen on the Owner's two-USB board was not readable in the photo. Before
the first power-up with the module on, confirm red = 3.3 V and black = GND (multimeter across them
with the deck on USB and the module off, or read the silkscreen zoomed in).

**Mounting (to decide with the Owner):** the dome needs line of sight to the seats, through a hole or
a thin IR-transparent window in the deck's green case. Keep it out of direct sunlight through the
windscreen (sunlight floods VS1838B receivers and drops presses). Wires under 20 cm need nothing else.

## The remote

Generic 24-key RGB LED-kit remote, almost certainly **NEC, 38 kHz** (unconfirmed until the test).
Layout, top to bottom, left to right:

| Row | Buttons |
|---|---|
| 1 | brightness up (☀▲), brightness down (☀▼), ON, OFF |
| 2 | RED, GREEN, BLUE, WHITE |
| 3 | ORANGE, YELLOW, CYAN, PURPLE |
| 4 | JUMP3, JUMP7, FADE3, FADE7 |
| 5 | ♪1, ♪2, ♪3, ♪4 |

All eight colour buttons exist as deck swatches (`ledlook::Colour`: RED 0, ORANGE 1, PINK 2,
PURPLE 3, BLUE 4, GREEN 5, WHITE 6, YELLOW 7, CYAN 8). Only PINK has no button.

## Proposed mapping (the Owner confirms before Task 3)

| Remote | Deck action | Existing path |
|---|---|---|
| ☀▲ / ☀▼ | both lights one 10 % step up / down; holding repeats | `ledvoice::Command::levelStep` ±1 |
| ON / OFF | both lights on / off | `Command::power` 1 / 0 |
| 8 colours | that colour on both lights | `Command::color` = swatch |
| JUMP3, JUMP7, FADE3, FADE7 | presets 1-4: ROSE, FIRE, GOJIRA, PURPURA | `Command::preset` 1-4 |
| ♪1, ♪2 | presets 5-6: CIVIC, OCEAN | `Command::preset` 5-6 |
| ♪3 | music mode toggle | `Command::music` |
| ♪4 | karaoke toggle | `Command::karaoke` |

The presets are `src/util/yellow/ledpresets.cpp` (six of them since the restyle; `ledpresets::N`).
Toggles need the current state (`musicOn`, `karaokeOn` in `ledpanel.cpp`), so the mapping returns
"toggle" and the panel resolves it.

## What exists now (branch `feat/irtest`, from `main` 4eea964)

- `src/diag/irtest.cpp`: standalone test, like `ps3test`/`blescan`. IRremote 4.4.1 on GPIO 27.
  The screen shows the command code in big 7-segment digits, then protocol, address, raw value,
  "(held)" for NEC repeat frames, and a press counter. Serial logs one line a press:
  `[ir] NEC addr 0x00EF cmd 0x03 raw 0x... (held)`.
- `platformio.ini` `[env:irtest]`: extends `cyd`, `lib_deps` TFT_eSPI + `z3t0/IRremote@4.4.1`,
  `LOAD_FONT7`, and **`build_src_flags =` (empty)**. IRremote is header-only and has deliberate
  `#warning`s plus a `#pragma GCC diagnostic ignored "-Wvolatile"` that GCC 8 doesn't know, so it
  can't compile under `src/`'s `-Werror`. Pragmas around the `#include` don't help (`-Wcpp` and
  `-Wpragmas` fire anyway).
- Built: `pio run -e irtest` succeeds (RAM 7.1 %, flash 335 KB). Not flashed.

`feat/pad-redesign` (the PS3 controller redesign, unmerged on 2026-11-12) also changes
`ledpanel.cpp`'s input handling. Start Task 3 from `main` after it merges, or rebase onto it.

## Tasks

### 1. Capture the codes (with the Owner, deck on USB)

1. Confirm the 3.3 V / GND wires (above), then flash the test: `pio run -e irtest -t upload -t monitor`.
   Flashing over USB swaps to `huge_app.csv`; NVS stays at 0x9000 in both tables, so the touch
   calibration and the looks survive. `pio run -e ledpanel -t upload` brings the panel back.
2. The Owner presses each of the 24 buttons once, in the table order, then holds ☀▲ for two seconds.
3. Record protocol, address and command per button from the serial log in the table in Task 2.
   Check that all share one address, that the commands are unique, and how often a held button
   repeats (NEC: a repeat frame every ~110 ms).
4. If nothing arrives: wiring (S on IO27?), then whether the module LED blinks on a press (if the
   module has one). If presses come in as UNKNOWN: distance/angle, else the remote isn't NEC and the
   raw values are what to map.

### 2. `util/yellow/irkeys`: pure mapping, host-tested

- `src/util/yellow/irkeys.h` (+ `.cpp` if it grows): `bool irkeys::lookup(uint16_t address,
  uint8_t command, Key* out)` from a fixed table (the codes from Task 1), and
  `bool irkeys::command(Key k, bool musicOn, bool karaokeOn, ledvoice::Command* out)`: the
  mapping above, toggles resolved from the state passed in. A wrong address or an unknown command
  returns false (the neighbour's TV remote does nothing).
- Repeat policy as a pure function: only brightness keys act on repeats, at most one step every
  ~250 ms; every other key acts on the first frame only.
- `test/test_irkeys/test_irkeys.cpp`: every button maps, unknown codes and foreign addresses don't,
  toggles flip from both states, repeats only step brightness and are rate-limited. Run through
  `tools/run_tests.ps1` like the other suites.

### 3. Receive in the LED panel

- **Library outside `src/`:** wrap IRremote in a tiny private library, `lib/irrx/` (`irrx.h`
  declaring `begin(int pin)` and `bool poll(uint16_t* address, uint8_t* command, bool* repeat)`,
  `irrx.cpp` the only file that includes `IRremote.hpp`). PlatformIO builds `lib/` without
  `build_src_flags`, so `src/` keeps `-Werror` and `ledpanel` needs no exemption. Add
  `z3t0/IRremote@4.4.1` to `[env:ledpanel]` `lib_deps`. Then `irtest` can use `lib/irrx` too and get
  its `-Werror` back.
- `pins.h` under `BOARD_CYD`: `static const int PIN_IR = 27;  // KY-022 on CN1`.
- `ledpanel.cpp`: `irrx::begin(PIN_IR)` in `setup()`; in `loop()`, poll, map with `irkeys`, then apply.
  Refactor `applyVoice` so the change itself (`karaoke` / `music` / `preset` / `bothlook::Change`
  branches) is a function that returns the description line, with `answerVoice` left to the voice
  path. The IR path shows the same line on screen with `setMessage` + `drawLooks()`, as `padPreset` /
  `padLevel` do. Zone is always BOTH.
- Log each acted press: `[ir] cmd 0x.. -> <line>`, and ignored codes once per code, for tuning.

### 4. Checks on the car hardware

The yellow deck is tight: Bluedroid in dual mode (BLE for the two ELK lights, Classic for the PS3
pad), WiFi for `/say`, heap low-water ~41 KB (`docs/yellow-deck.md`). Check on the real deck:

- **Heap:** IRremote's receive state is a few hundred bytes, but note the `[mem]` lines before/after.
- **Timer:** IRremote on the ESP32 Arduino core 2.0.x (platform espressif32@6.9.0) samples the pin from
  a hardware-timer interrupt every 50 µs. Confirm no other code in the panel claims that timer, and
  that the ISR is in IRAM: press buttons while `save()` writes NVS (flash cache off) and while
  music mode streams, and watch for a crash or garbled codes.
- **Coexistence:** presses during a BLE reconnect (`linkTask`), with the PS3 pad connected, and
  during a karaoke poll all decode and act.
- **Range and light:** from both front seats and the back, and in daylight.

- The black deck (S3): it has free pins too (GPIO 4-18 minus what its codec and I2C use), but the
  yellow deck is the one that drives the lights.
- Learning new remotes on the deck: the table is fixed in firmware.
